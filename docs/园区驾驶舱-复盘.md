## 二、踩过的坑（按代价排序）

### 1. 压缩模型不能动结构
**现象**：压完之后秋天晴天满地积雪、中央大厅的环形轨道消失。
**原因**：`gltf-transform optimize` 默认开 `flatten / join / palette`，会把节点名和层级打平。而前端**靠节点名**判断季节遮罩（`Snow_*`、`Autumn_*`）、接口（`Port_Main_*`）、细节件。
**规则**：只要下游按名字/层级取语义，压缩就必须 `--flatten false --join false --simplify false --instance false --palette false`。压完必须验三件事：三角面数是否与原版一致、关键节点名是否还在、同一机位像素差是否 <1%。

### 2. 外部 agent 会静默卡死
**现象**：派给 Claude 的任务跑了 67 分钟，日志 0 字节、文件 51 分钟没动。
**规则**：派单时记录文件基线；**超过 15 分钟无文件变更就判定卡死**，直接终止接管，不要等。中转站 503 时它会直接挂住而不是报错。

### 3. 不能采信 agent 自报的"已完成"
**案例**：它报"演示时间轴 08:39/13:30/20:10 正常"，实测是 11:01/16:00/13:17 且时间会倒退。它测的是"相机不动"的场景（`fly:false`），测不出真实飞行下的问题。
**规则**：验收必须用**用户实际使用路径**复现（真实点击、真实飞行、真实刷新），并且要数字和像素，不接受"我看过了"。

### 4. 前端说"在跑"必须是真数据
**案例**：进度环一开始只认 cron，后来为了好看挂了个假标记 `project_active.json`，导致某个群永远亮环；用户一眼看穿。
**规则**：状态类 UI 一律读真实数据源（本项目是 Hermes 自己的 `state.db`：`sessions` + `messages` + `session_turn_leases`）。判定"正在跑"用**回合是否结束**（最后一条 assistant 是否带 tool_calls），不要用"最近 N 秒有消息"，否则答完还要挂几分钟。

### 5. 相机决定天空是否存在
**现象**：写了完整的天穹着色器、云和太阳，用户说"看不到天空"。
**原因**：默认相机俯角 50°，地平线在画面外，天空根本没进视野。
**规则**：天空类效果必须先确认**取景**——先把相机放到能看见地平线的角度（俯角 ≈70°+），再谈云和太阳。

### 6. 中文写云表必须走 UTF-8 通道
**现象**：用 `curl -d` 传中文建待办，云表里落成乱码，还顺手建出一条重复条目。
**规则**：写飞书一律走 Python/API 的 UTF-8 路径；建之前先按关键词和截止日查重。

### 7. 挂着的 cron 会变成"僵尸"
**现象**：一次性任务跑完仍留在表里，还有 7 条 paused 却以为在工作的任务（改了调度也不会跑）。
**规则**：一次性完成即删（删前归档报告）；每周巡检专门查 `state=paused` 但本该在跑的任务。

## 三、可复用的方法论

### 「先量化再动手」
每个改动前先拿到基线数字：帧率、三角面、批次数、CPU 占比、体积、亮度差。改完用同一套脚本再测一遍。这个项目里所有"改好了"的结论都是脚本跑出来的，没有一句是"我觉得"。

### 「像素级验收」
亮度是否一致、压缩是否失真、聚焦是否压暗——这些问题肉眼容易吵架，用 PIL 取区域平均亮度/逐像素差就能一句话定案（本项目 0.25% 判为无损、0.6% 判为可忽略）。

### 「减法优先」
删掉分区体系、删掉资料页、删掉重跑按钮、删掉 26 条 cron——每一次减法都让系统更清楚。加功能之前先问"这个能不能不建"。

### 「一个业务一条任务」
同一件事拆成多条 cron，最终一定会失控（抢座被拆成 7 条）。周内差异（周一约周三、周二不约周四）写进脚本内部，不要靠建新任务表达。

## 四、性能优化的具体手法（可直接抄）

| 手法 | 做法 | 效果 |
|---|---|---|
| 空闲降帧 | 3 秒无操作 + 无连续动画 → 8fps；指针/键盘立刻回满帧 | 帧数 −87% |
| 脏渲染 | 只有状态变化才重绘，切后台完全不画 | 静置 CPU 6% |
| 阴影按需 | `shadowMap.autoUpdate=false`，太阳方向变才重算 | 阴影从每帧变每 30 秒 |
| DPR 上限 | 中画质 1.5→1.25 | 填充率 −30% |
| 模型压缩 | meshopt + webp，保结构参数 | 230MB→53MB |
| 着色器预热 | 加载后预先编译入夜要用的程序 | 入夜卡顿 3.7s→0.14s |

## 二、六条心得

1. **压缩/合批这类管线，先问下游靠不靠名字。** 一次默认参数的优化，能同时造出"积雪"和"轨道消失"两个看似无关的 bug。
2. **状态类 UI 必须接真源，宁可显示"未知"。** 假标记骗得过眼睛，骗不过用户的一次点击。
3. **"在跑"要按回合计，不按时间窗。** 用"最近 N 秒有消息"判活，答完还会挂几分钟；看最后一条消息是不是带工具调用的 assistant 才准。
4. **验收要量。** 亮度差、时间轴、压缩失真，全部用脚本出数字；外部 agent 的"实测数字"一律复核。
5. **外部 agent 会静默卡死，也会为了凑你的错数字扭曲实现。** 派单给硬锚点前自己先算一遍；15 分钟无产物就接管。
6. **减法优先。** 删分区、删资料页、删重跑、删 26 条 cron——每次减法都让系统更清楚，也更好验收。
